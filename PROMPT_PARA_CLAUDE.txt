2) FLUJO POST-REGISTRO: CREAR ALMACÉN O UNIRSE
- Al terminar de crear cuenta e iniciar sesión, si el usuario no pertenece a ningún almacén mostrar dos opciones claras:
  A. “Crear un almacén”: nombre del negocio y nombre del almacén. Crear todo en Supabase y mostrar el código único del almacén al propietario, con opción para copiarlo.
  B. “Unirme a un almacén”: campo para introducir código de almacén, normalizar espacios/mayúsculas, validarlo de forma segura en PostgreSQL y registrar al usuario como integrante del almacén.
- Código incorrecto: mensaje amigable, sin revelar datos de otros negocios.
- Código correcto: asociar el usuario al negocio y al almacén concretos, asignar rol operator por defecto, sin permisos financieros ni administrativos.
- El código no debe ser una contraseña ni conceder permisos adicionales. Solo permite solicitar incorporación. Validar autenticación y realizar la operación en función RPC SECURITY DEFINER con search_path fijado y nombres de tablas totalmente calificados.
- Si el modelo permite varios almacenes por negocio, el usuario solo debe ver los almacenes a los que tiene acceso. Guardar warehouse_id en la relación de membresía y aplicar RLS por almacén. No dejar que un usuario de un almacén pueda leer inventario de otro por compartir business_id.
- No crear membresías desde el navegador mediante insert directo si una RPC segura puede hacerlo.
- Si se cambia el esquema, crear una migración nueva, idempotente cuando sea posible, compatible con usuarios/datos existentes. No pedir que borre la base ni que repita la migración inicial.

3) AUDITORÍA DE MOVIMIENTOS CON EL NOMBRE DE QUIEN ACTÚA
- Cada movimiento de inventario debe guardar user_id autenticado y un snapshot del nombre visible del usuario al momento de registrar el movimiento (profiles.full_name o el nombre que la persona capturó durante registro). Si falta nombre, usar una alternativa no vacía, por ejemplo la parte anterior a @ del correo.
- Guardar también snapshot de producto y unidad para que el historial/reporte siga siendo correcto aunque se renombre el producto después.
- La función RPC record_inventory_movement debe obtener auth.uid() en servidor; nunca confiar en un user_id enviado desde el frontend.
- El registro debe ser transaccional: validar cantidad positiva, existencia suficiente para salidas, permiso de acceso al almacén y actualización de stock y registro de movimiento en la misma transacción.
- Mostrar columna “Registró” en historial, y nombre de usuario en PDF. No permitir que el usuario edite o suplante quién hizo un movimiento.
- La información histórica previa a la migración debe rellenarse cuando sea posible con profiles y productos existentes; si no, mostrar “Usuario sin nombre”/“Dato histórico no disponible”, sin inventar identidades.
